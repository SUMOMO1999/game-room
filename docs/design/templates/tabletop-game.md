# 桌游类设计模板

适合内容目录较多、卡牌或物件各有用途、可能加入扩展的游戏，也适合飞行棋、大富翁这类以棋盘、棋子、骰子或资产为核心的游戏。分类看设计重心，不看材料是否真的叫“牌”：混合游戏可以同时采用[总模板入口](../game-design-template.md)列出的两类模板。

朋友先填第一部分，用普通话和局面例子即可，不需要跑代码。卡牌较多时，把每种牌复制到[逐卡定义模板](card-definition.md)；飞行棋没有卡牌就写“不适用”，改为完整棋盘、棋子与骰子定义。第二部分按实际机制选填，第三部分由维护者补全。

本模板是设计要求，不代表棋牌室已经实现通用卡牌引擎、扩展系统、交易或战役存档。关键歧义写“待确认／确认人／影响”，开发者与 AI 不得代替玩家决定。朋友变体与商业参考的规则分别记录，名称、美术和文本不直接复制。

设计后由维护者先按[技术实施计划模板](../../plans/game-implementation-plan-template.md)评审模块、状态／权限、动作／并发、内容数量、资源与真实共通接入、兼容／恢复和回退，再做Step 0与完整实现。朋友不用补技术合同，不能把设计已有当成可以跳过计划。

## 第一部分：必须写清的本轮游戏

### A1. 目标、范围和版本

- 游戏名称、别名、一句话目标：［填写］
- 人数上下限、合作／竞争／组队、队伍组成：［填写］
- 本轮版本、规则提出者、确认人、确认日期：［填写］
- 本轮包含哪些基础内容与扩展？哪些暂不加入？［填写；不能仅写“所有卡以后补”］
- 一局预计时长、能否分多次玩、是否跨局保留进度：［填写］
- 参考规则书与朋友改动：［分别填写来源、版本和差异］
- 新人如何理解玩法：［写三到五步入门；详细边界另放规则索引］

最终完整接入之前，本轮可能入局的全部内容必须有定义；未来尚未设计的卡不必现在全写。先让一套已定义、可完成整局的内容形成闭环，再扩充。

### A2. Step 0：资源样板与上屏验证

先明确 A1 的最小规则结构、实体种类和必需信息，再开始这一阶段；样板验证通过后才进入完整游戏实现，具体门槛沿用[资源阶段](../resource-stage.md)。这里的“资源”包括卡牌图案、数字和文字、棋盘、棋子、图标、牌背、选中与高亮效果、基础音效，不等于全部交给 AI 生成图片。

- 本轮资源清单和预估数量：［填写每种正面、背面、棋盘、标记、图标及音效］
- 代表性样板：［普通实体、最长规则文本、最相似的两类特殊实体、暗面、选中和不可用各一例］
- 制作方法与来源：［代码绘制／矢量／字体／AI 插画／自制音效；记授权、署名或限制］
- 卡面信息顺序：［名称、分类、费用、主要数值、图案、效果、编号分别在哪］
- 缩小后仍必须看清什么？需要点击放大的细节是什么？［填写］
- 私有背面、未解锁内容与公开资源目录会不会暴露不该公开的信息？［填写］
- 资源加载失败的可辨替代：［填写；不能几种特殊牌都变成同一个空框］
- 手机与电脑小样：［实际显示尺寸，密集桌面、大手牌、长文本、拖影、预览和放大］
- 真机检查：［手指点击／拖动、横竖屏往返、颜色与图形辨识、声音听感；列设备与结果］
- 样板通过标准、确认人、仍待验证条件：［填写］

先做可代表整套风格和信息密度的样板，列出全量补齐计划，再批量制作本轮资源。需要短小交互原型验证，不要求先做完账号、整局服务或所有卡图；纯规则验证也可以先进行。原型不得被记成正式成品已验收。完整接入与交付前还要检查本轮全部可入局资源和发布后的资源路径，未补齐的内容明确排除。

### A3. 完整材料目录与分类

为每种可入局的材料重复以下记录；相同规则的不同数值可用明确生成规律加完整取值范围，不能把独立效果藏在一句“类似其他牌”里。

- 类型编号与显示名称：［填写；编号固定且不因改名或排序改变］
- 材料类别：［卡牌／棋子／格子／骰子／标记／钱币／资产／角色／其他］
- 本轮数量或生成规律：［填写人数、难度或房间参数对应数量与上下限］
- 规则分类、标签与关键词：［列准确含义；装饰性标签注明不参与规则］
- 所属基础包／扩展／场景、定义版本：［填写］
- 定义位置：［逐卡文件或本文章节链接；不能只给一张图］
- 资源位置与状态：［样板／完成／待制作；区别规则待确认与美术待制作］
- 是否可进入本轮对局：［是／否；需要哪些已确认条件］

**不同卡名、相同类型标签，不等于相同效果。** 如“事件牌”只是一个类别，“补给”“换位”仍须各有完整定义。分类用于说明、筛选或明确规则条件，不自动赋予玩家读取或操作权。

非卡牌实体也必须定义：棋盘的格子与连接、方向与距离；棋子的状态和移动；骰子的面与分布；资产的收入与所有权；标记的上限、归属和清除时机。棋盘示意图之外还要有编号与可达关系。

### A4. 区域、归属与信息

为每个区域重复：

- 区域名、用途、容量：［如公共桌面、每人手牌、抽牌堆、弃牌堆、商店、棋盘格、移出区］
- 有无顺序、朝向、堆叠、附着或占位关系？怎样移动？［填写］
- 所有者、当前操作者、位置持有者是否相同？怎样转移？［填写］
- 所有人、本人、队友和观众分别看见什么？牌背、张数、类型、顺序哪些公开？［填写］
- 什么时候揭示，揭示后能否重新隐藏？［填写］
- 空了、满了、来源不足或目标位置不能放时怎么办？［填写］

同名同图的两张卡仍是两件物品；不能把它们交换身份来撤销费用、复用次数或避开效果。重新混入秘密牌堆时，要说明其他人是否允许继续追踪此前公开的那一张。

### A5. 开局和阶段

- 初始化完整材料、布置棋盘、发牌／抽取／选择／竞拍的顺序：［填写］
- 先手、座位和队伍怎样确定；显示顺序如何与规则行动顺序对应：［填写］
- 全局轮次、个人回合与阶段分别是什么：［用箭头写一整轮］
- 每阶段由谁行动：［一人／多人分别选／所有人同意／系统结算］
- 阶段如何结束、怎样换人，是否加手、跳过、逆序或插入回应：［填写］
- 每阶段能做什么，必做什么，能否放弃；无合法行动怎么办：［填写］
- 本游戏的倒计时及超时默认动作：［填写；涉及等待选择时不要漏掉］
- 开局后能否旁观、入座、替补或改变阵营：［引用共通房间设计并注明差异］

### A6. 所有行动的定义

不要只写“出牌”“触发”“按牌面说明”。对每种玩家或系统行为重复以下记录；逐卡特殊行为可链接卡定义，不必复制两遍。

- 行动名称、发起者、可用阶段：［填写］
- 来源区域、对象与前提：［填写；对谁的什么物件做什么］
- 选择什么，谁选择，什么时候选，是否允许自己／队友／同一对象重复选：［填写］
- 费用与限次：［全部费用、额外费用、减免、每回合／每轮／整局次数］
- 何时确认，确认前后各能否取消；已付费用和已揭示信息怎样处理：［填写］
- 执行步骤与每步结果：［按序列出资源移动、信息揭示、数值变化及后续选择］
- 没有目标、目标后来失效、来源不足、其中一步做不到：［分别写结果与是否退费］
- 下一阶段和行动者、是否消耗行动或结束回合：［填写］
- 可见反馈：［谁看见怎样的文字、高亮、动画与声音；谁只见到公开结果］
- 普通合法例子、非法例子和最易争议的例子：［都写前后完整局面］

费用是行动的前提，效果是行动产生的结果，两者不能混写。比如“弃一张牌作为费用”和“抽一张后弃一张”会在不同时间失去不同信息；具体游戏必须人工确认这些差异。

### A7. 逐卡、逐物件的效果

卡牌逐种使用[逐卡定义模板](card-definition.md)。共同字段由基础规则定义，各卡引用；独有例外必须明确写出。定义深度以“玩家和开发者面对同一局面能得到同一个结果”为标准。

至少能回答：在何时、由谁、从哪里使用；付什么；影响谁或什么；按哪几步做；持续多久；结束或取消后卡到哪里；缺目标、缺材料或中途失效怎么办。不是每张卡都需要反应、持续、替换、复制等机制；没有就写“无”。

角色能力、棋盘格效果、骰子奖励、装备和资产也采用相同深度；名称替换成“能力／物件／格子”，不是一律改造成卡牌。

### A8. 胜负、结算、离场与完整例子

- 触发结束的全部条件，何时检查，是否先完成当前效果或回应：［填写］
- 个人／团队胜负、并列、共同失败、积分公式与跨局保留：［填写］
- 先淘汰、破产、认输、离房、全员离线的区别和后果：［填写］
- 提和、暂停、再来一局、结束后的查看与退出：［引用平台并写本游戏差异］
- 有限材料耗尽、无人能动、重复局面、效果链不能结束：［填写已确认玩法后果］
- 至少一个从开局到结局的完整演示：［覆盖全部阶段、资源流向与结算］
- 至少一个超时例子、一个中途恢复例子、一个争议边界：［填写］
- 未定问题与确认人：［逐项写；影响开局、动作、秘密或结算的未知不得略过］

## 第二部分：按需机制，采用才展开

先标明每项“采用／不采用”。一张卡引入新机制，就连同该机制一起设计和验证；只增加图案或数值时无需引入整套复杂结构。下面的问题用于发现缺口，不预设某种商业游戏的答案。

### M1. 回应、打断与同时触发

- 哪些行为允许回应，窗口在费用前／费用后／效果前还是效果后：［填写］
- 谁先获得回应权，谁可以放弃，所有人放弃后何时关闭：［填写］
- 多个效果由同一事件触发时怎样排序？谁决定，依据哪些公开信息：［填写］
- 效果触发、进入待处理区与正式执行是否分开？是否允许再次回应：［填写］
- 回应超时、断线、玩家退场及目标改变怎样继续：［填写］
- 连锁何时终止，是否允许无穷循环，有哪些明确的重复限制：［填写］

简单游戏可以直接顺序执行已确认的效果；只有确实需要“先回应、后结算”的玩法才设计回应窗口或待处理队列，不默认使用万智牌的栈。

### M2. 持续、状态与替换

- 一次效果、持续加成、状态标记、延迟触发、替换／阻止分别有哪些：［分开列］
- 持续的起止边界、附着对象与来源离开后的结果：［填写］
- 两个加成、减免、设定值或禁止冲突时的顺序和优先级：［填写并给具体数字例子］
- 替换在原动作发生前还是之后判断；原动作没有发生时会不会触发后续：［填写］
- 多个替换适用时谁选择、是否能依次适用、怎样避免重复替换自身：［填写］
- “禁止”和“允许”冲突、文本与基础规则冲突时哪个规则生效：［由本游戏明确；不借名词默认］

### M3. 随机、秘密和多人选择

- 洗牌、抽牌、掷骰、随机事件与概率范围：［填写］
- 什么时候固定结果，哪些结果只对特定玩家揭示：［填写］
- 随机结果后的选择是否必做、能否放弃，超时选择是什么：［填写］
- 同时选择是否互相保密，锁定后何时一起揭示，谁先执行：［填写］
- 无目标或没有材料时是取消、做可做部分、换目标还是结束：［逐机制确认］
- 重连后继续哪次结果或哪份已锁定选择：［填写；不能刷新重抽］

### M4. 交易、资产、阵营和战役

采用才补充：交易对象、报价版本、必要确认人、有效期、失效条件；货币单位、银行发行、所有权、债务与破产顺序；阵营切换与秘密权限；战役分支、解锁、奖励和跨局存档。具体展开方法沿用[共通实现设计](../game-design-template.md)中的适用模块与[平台设计](../platform.md)，不得默认套用大富翁的费用或破产规则。

### M5. 复制、变形、生成与销毁

- 复制的是印刷定义、当前数值、已选择目标还是持续状态：［填写］
- 新副本有哪些独立身份、归属、使用次数和到期条件：［填写］
- 变形后的类型、旧状态、费用和附着关系怎样处理：［填写］
- 合法生成／销毁是否改变材料总量，哪些规则允许，事件怎样记录：［填写］

没有采用这些效果就写“无”，不能因为准备扩展而先实现无限生成或任意脚本。

### M6. 扩展、内容修订和组合

- 内容包标识、版本、依赖和互斥：［填写］
- 每次开局允许哪些包组合，是否影响人数、材料量、阶段或胜负：［填写］
- 每张新增牌引用哪些已支持行为，是否需要新机制：［填写］
- 新机制与旧机制的重点交互：［列配对及代表性组合，不要求证明所有任意组合］
- 改数值／改文字／改效果／换资源分别怎样定版本：［填写］
- 每局固定的版本组合：［分别填写规则版本、内容目录版本、资源清单版本；共同组成不可悄悄替换的本局 bundle］
- 存档格式版本与上述三类版本怎样区分；旧局如何用原 bundle 恢复，缺失或不兼容时如何明确拒绝：［填写］
- 尚未支持的内容如何在开局前明确阻止：［填写；不允许抽到才临时解释］

新内容按“完整定义 → 资源 → 行为实现 → 交互用例 → 加入可用目录”推进。已经开始的局不能因发布新卡或更换最新定义而突然变规则。即使卡编号相同，也要恢复当时的完整版本组合，不能只保留旧卡面文字却执行新效果。存档格式迁移另行设计、验证并记录，不能借迁移默默改旧局规则。

## 第三部分：维护者完成实现和验收设计

账号、稳定成员、玩家／观众角色、连接、聊天、声音、安装和退出沿用[共通平台](../platform.md)。这里补本游戏差异，不重建账号生态。以下全部是开发前需要明确的合同，不是“已经实现”的能力。

### D1. 目录、实体与效果实现

- `typeId` 是一种已定义卡／物件的固定编号；`copyId` 是本局某一份实体的唯一编号。两张同种牌共享 `typeId`，必须各有 `copyId`，移动、保存、选择和去重都指向正确实体：［写本游戏方案］
- 权威实体的类型、版本、归属、位置、顺序、朝向、计数器和已用次数：［列字段及不变量］
- 隐藏实体重新混入时，权威 `copyId` 稳定，客户端可见代号如何重置或不公开：［填写；不能用可预测 ID 暴露身份或牌序］
- 行为名称、参数、前提、范围、结果及可用内容的映射：［填写］
- 卡面文字与权威效果定义怎样保持同一版本并相互核对：［填写；翻译或美术不能偷偷改变效果］
- 目录完整性检查：［唯一编号、数量、引用目标、未知效果、缺资源、禁用组合都如何在开局前拒绝］

优先用受审阅的行为函数和明确参数实现本游戏实际需要的效果；能复用时再抽公共部分。朋友提交的是设计内容，不是可任意执行的 JavaScript 卡脚本。新增机制仍需维护者开发、测试并纳入受支持清单；不能把“填写新卡”宣传成无需开发的万能引擎。

### D2. 权限、持久选择、随机和原子保存

- 玩家、队友、观众和系统分别得到什么投影；提示、日志、事件、资源及错误文案怎样防泄漏：［填写］
- 谁可以操作目标，按成员／角色／阶段／规则逐项校验；标签不能代替权限：［填写］
- 每次确认的成本、结果、随机值、后续选择、事件和修订怎样一起保存：［填写］
- 待选择记录：［选择人、阶段、合法范围、已付成本、固定随机结果、截止时间、完成状态］
- 请求去重、并发回应、超时竞争、响应丢失与重试读取：［填写］
- 恢复阶段、回合、效果队列、持续状态和每人秘密；损坏／未知版本怎样拒绝：［填写］
- 基础材料的守恒公式与合法生成／销毁记录：［填写］

选择未完成时可以存成明确的待处理阶段，不能用“先扣钱、后靠客户端补结算”替代完整状态。保存成功但没收到回复时先读确认结果，不再抽卡、掷骰、扣费或多处理一次触发。

### D3. 页面、交互与反馈

- 按[共通接入记录](../platform.md#共通能力接入记录)写房间／练习范围、真实模块／控件／样式、通知避让、状态归属与证明层级；无房间成员的练习明确无联网聊天。
- 主屏必须同时可见的区域、低高度和密集内容的阅读方式：［填写］
- 卡牌／棋盘的逻辑顺序、正式位置、私人整理和方向变化投影：［分开定义］
- 点击、拖动、整组、目标选择、撤销、确认及放大分别允许什么：［填写并演示落点］
- 多步骤选择显示当前步骤、剩余费用、可取消范围；失去操作权怎样清理：［填写］
- 本人回合、待本人回应、别人最新公开变化、新材料、本人和他人聊天：［分别写视觉提示］
- 每类动作的本人／公共声音、静音替代、恢复去重和启声入口：［填写］
- 手牌／桌面／拖影／预览／放大都加载对应资源，未知或加载失败怎样显示：［填写］
- 小屏、平板、大屏、长昵称、长文本、软键盘及横竖往返的验收场景：［填写］

### D4. 必须验证的例子与交付条件

每项写“初始局面与身份 → 行动 → 正式结果与可见反馈 → 证明方法”。简单游戏删去不适用项并注明理由；复杂游戏按采用的机制追加。

1. 完整一局，全部阶段与结局；本轮全部可入局类型均有定义、资源和执行用例：［填写］
2. 每类费用的足额／不足、合法／非法目标、空区域、材料不足和不可完成步骤：［填写］
3. 目标改变、同一事件多触发、持续到期、替换冲突：［采用时填写］
4. 对手和观众看不到手牌、秘密选择、随机序列或可预测实体身份：［填写］
5. 重复请求、响应丢失、并发选择、超时、退场及随机结果后的刷新／换设备：［填写］
6. 私人布局、公共布局、临时预览、正式规则状态各自在取消、确认、旋转和恢复后的结果：［填写］
7. 扩展组合、同编号旧定义、禁用内容、未知行为和损坏存档：［采用时填写］
8. 真实手机阅读和触摸、键盘聊天、声音、多人反馈与稳定出口：［填写设备及结果］

允许开始完整实现的条件：最小闭环、本次实施的关键规则与代表性内容定义已人工确认；Step 0 样板通过，全量补齐计划明确；权威状态、动作与验收能对应第一部分的例子。尚未明确或补齐的内容不得启用，未知机制可先用隔离原型验证。完整接入与交付之前，本轮全部可入局定义和资源齐备，规则、权限、保存、失败和设备体验有实际结果；未验证的真机或联合场景明确留下，不以测试条数冒充全部通过。

## 参考方法与来源

阅读日期：2026-10-06。以下只借鉴设计组织与检查方法，不采用来源游戏的机制默认值，也不引入其代码框架。

- [Board Game Arena：ItemManager](https://en.doc.boardgamearena.com/ItemManager)：物件身份、所在区域与区域内顺序分开建模。本文采用独立类型／副本和区域定义；不会因整理顺序改变权威实体身份。
- [Board Game Arena：State classes](https://en.doc.boardgamearena.com/State_classes:_State_directory)：阶段可由一人、多人或系统处理。本文据此要求逐阶段写行动者、合法动作、后续阶段与私人选择。
- [boardgame.io：Secret State](https://github.com/boardgameio/boardgame.io/blob/main/docs/documentation/secret-state.md)：隐藏信息应在发送前形成玩家可见投影，秘密相关动作可只在服务端处理。本文把这点写进权威数据与权限验收。
- [Magic 官方规则入口](https://magic.wizards.com/en/rules)及[综合规则文本 2026-09-25](https://media.wizards.com/2026/downloads/MagicCompRules%2020260925.txt)，§118、603、608、616：费用、触发、目标与结算、替换有独立定义。本文仅把这些区别转成待确认问题；回应顺序、目标失效和退费均由本游戏另定。
