# 新游戏设计模板

## 先选分类模板

只确定了游戏名时，先按[从游戏名到一版设计](from-game-name.md)圈定模式、版本与初版内容。

- **固定牌类**：复制[固定牌组与规则模板](templates/fixed-deck-game.md)。适合扑克、麻将、414、拉密等材料组成有限、主要依赖数字/花色/组合与轮转规则的游戏。
- **桌游类**：复制[内容与行为模板](templates/tabletop-game.md)，有独特卡牌时配合[逐卡定义](templates/card-definition.md)。适合不同卡牌/角色/地块各有行为、会增加扩展内容的游戏。飞行棋、军棋可用轻版，卡牌章节写“不适用”，仍定义适用的棋盘、棋子、随机过程和操作。

按设计重心选择；有大量牌的游戏也可能属于桌游类，固定材料游戏同样需要资源。混合游戏选一个主模板并补另一类必要字段，不重复定义相同内容。本页完整共通字段保留，供维护者查漏或处理难分类玩法。

两类都先明确设计，由维护者使用[技术实施计划模板](../plans/game-implementation-plan-template.md)编写并评审模块、数据／权限、接口／并发、资源、兼容、验收与回退，再进入[Step 0：资源样板与上屏验证](resource-stage.md)，通过后完整实现。计划不能只有流程名称，本轮全部内容的数量与质量、真实共通接入和停止条件要具体。最小规则骨架先明确，本轮所有可入局内容在接入前定义完，未来扩展不用现在穷举。[参考来源与采用范围](reference-notes.md)说明借鉴依据。

朋友只需阅读设计、讨论玩法并填第一部分，不用安装或运行代码，也不用提交 PR。可直接提供文字和实际例子，由维护者整理为 `docs/proposals/<game>.md`；愿意使用 GitHub 的朋友也可以在文件或 PR 中协作。第二部分由维护者／开发者根据已确认规则补全。[设计入口](./README.md)收录已定游戏，[共通平台设计](./platform.md)负责账号、房间、观众、连接、聊天、声音及安装体验。

填写时保留具体例子。不了解的规则写“待确认”，给出问题和确认人；关键规则没定时，开发者和 AI 都不能自行补成一种玩法。像“414”这样的简称先写清所指游戏、当地叫法与版本，不依据名字预填规则。

## 第一部分：朋友填写玩家规则

### A1. 这是什么游戏

- 游戏名称、别名：［填写］
- 这次要玩的版本／朋友约定：［填写；哪些规则与其他玩法不同］
- 规则提出者与确认人：［填写］
- 本稿状态：［草稿／有争议／规则已确认］
- 需要几个人？允许几人到几人？是否组队，队伍怎样组成？［填写］
- 用什么材料？每种牌、棋、钱、资产或道具分别多少？［填写］
- 用一句话解释目标：［填写］
- 有原规则书或可公开引用的来源吗？［填写；没有也可说明为朋友自定］

### A2. 怎样开始

- 初始场面、每人得到的材料、共同区域是什么？［填写］
- 如何选先手、座位、阵营或队伍？谁决定或执行随机过程？［填写］
- 玩家从开始就能知道什么？哪些内容只属于自己、队友、某几人或所有人？［填写］
- 是否需要发牌、选角色、布阵、竞拍等开局步骤？按什么顺序，什么时候算完成？［填写］
- 新玩家能否中途加入？旁观者能看见什么？［填写］

### A3. 一个回合怎样进行

先用普通话写出一位玩家从轮到自己到结束的完整过程，再补下面的问题。

- 轮到谁，由什么决定？每次固定下一位，还是可能加手、跳过、逆序或插入其他人？［填写］
- 回合是否分阶段？例如随机结果→选择→行动→结算。每阶段能做什么，怎样进入下一阶段？［填写］
- 哪些动作合法，各自前提与结果是什么？哪些动作必做，哪些可放弃？［填写］
- 一回合最多做几次？哪些动作结束回合，哪些只是查看、选择或整理？［填写］
- 玩家能撤销到哪一步？确认之后能否反悔？［填写］
- 不轮到自己时能做什么？例如回应交易、竞价、反应牌、求和或聊天。［填写］
- 没有合法动作时怎么办？［填写］

不要只写“正常出牌”或“按常规”。例如涉及拆组、换牌、连吃、连翻、携带、交易，须说清每个对象从哪里来、到哪里去，行动后还剩什么。

### A4. 胜负、积分与离场

- 什么时候结束？赢家、输家、和局分别如何判断？同时满足多个条件时谁优先？［填写］
- 分数怎样计算？单位、正负、并列、队伍分配与跨局累计分别是什么？不计分则明确写“不计分”。［填写］
- 是否有人先淘汰／破产，而其他人继续？离场者怎样排名，资产或道具交给谁？［填写］
- 能否认输、提和、暂停？由谁同意，未回应是否有期限？［填写］
- 每手或每阶段有没有时间限制？超时执行什么，是否保留已确认的部分结果？［填写］
- 断线、返回大厅、退出房间分别怎样处理？与认输是否相同？［填写］
- 连续无人行动、反复局面、材料耗尽或不能完成必做步骤时怎么办？［填写］

房间成员和连接通常沿用平台约定；如果本游戏需要不同的玩法后果，应在这里提出并确认，而不是默默改掉共通行为。

### A5. 用例子讲清规则

至少写三个完整例子，每个包含“开始局面→谁做什么→是否合法→结果和下一位”。不要只给最后结果。

1. **普通合法行动**：［填写］
2. **接近边界但不合法的行动**：［填写原因；拒绝后局面怎样］
3. **最容易争议的情况**：［填写；若未定，列出不同主张］

有隐藏信息、随机结果、交易、携带或多人同时回应时，再各写一个相关例子。胜负／并列、超时和离场也至少各有一个例子。

### A6. 争议与未知

每个未定问题单独列出：

- 问题：［填写］
- 目前有哪些选择，各自例子是什么：［填写］
- 谁负责确认：［填写］
- 确认结论和日期：［确认后填写］
- 哪些玩法因此暂不能开发或验收：［开发者补充］

已确认的版本是本轮开发依据。以后改规则另定版本，旧局如何继续由第二部分说明；不能用新的解释悄悄改变进行中的局。

## 第二部分：开发者补全实现设计

### B0. 资源阶段与本轮内容范围

- 分类模板、本轮规则/内容范围及最小材料清单：［填写］
- Step 0资源清单、样板和可操作上屏结果：［填写；按resource-stage.md记录］
- 允许进入完整实现的范围、尚缺资源/定义及责任人：［填写］
- 本轮每种可入局内容的定义编号与资源映射：［填写；副本共用类型定义］
- 内容、规则、资源及存档版本对应关系：［填写；新效果不重解释旧局］

后续完整实现不能跳过样板门槛；隔离原型与正式完成分别记录。繁多内容引用逐卡目录，不能把“卡面写什么就做什么”当作行为规格。

这一部分把第一部分转成可执行、可存档、可验证的合同。引用[共通平台](./platform.md)，只写本游戏差异，不复制账号、房间和聊天规范。填“无需／不适用”比强行沿用拉密的牌架、拖影或出牌结构更准确。

### B1. 范围、参数与规则版本

- 游戏标识、显示名称、规则版本与已确认规则来源：［填写］
- 玩家范围、队伍、观众、开局材料与可配置参数：［给出类型、默认值、上下限及谁可在何时修改］
- 修改参数是否清准备？开局后是否锁定？［填写］
- 本轮实现内容、后续内容、练习／系统对手是否提供：［填写］
- 旧规则与旧存档恢复、显式新局和迁移策略：［填写；不允许默默重解释旧局］

### B2. 状态、阶段与行动

列出等待、开局步骤、各回合子阶段、暂停、结束和中止。每个阶段填写当前行动者；行动者可能是一人、多人、队伍、银行或其他系统角色，不能默认永远只有当前玩家可回应。

每项行动按下面格式填写，可重复：

- 行动名与页面入口：［填写］
- 谁能做、在哪个阶段、需哪些前提：［填写］
- 请求携带什么：［填写实体 ID、数量、目标、选择等］
- 权威校验与原子结果：［填写；包括材料移动、信息揭示、积分、随机结果及待回应事项］
- 下一阶段／下一行动者；是否消耗回合或撤销权：［填写］
- 失败原因与局面是否保持：［填写］

选择、高亮、放大和本机整理与业务行动分开。多步骤行动须注明哪些步骤只是草稿、哪些已确认并不可撤销；页面关闭、暂停或重连时停在哪一步。

### B3. 权威数据、权限与守恒

- 权威状态的完整字段和实体集合：［填写］
- 所有玩家、本人、队友、指定对象、观众各能得到什么投影：［填写］
- 本机显示状态、私人草稿和可共享预览各有哪些字段：［填写；没有则写无］
- 合法动作提示、错误文案、事件、日志和静态资源是否可能透露秘密：［逐项说明］
- 谁可以看与谁可以操作分别如何校验：［填写；房主／管理员不自动获得游戏权］
- 材料或资产守恒公式：［填写初始总量及每次转移；实体唯一 ID 不可复用］
- 合法生成／销毁来源：［如存在，注明规则与记账；不能靠无法解释的差额平账］

不要把客户端过滤当权限保护。提交只声明意图，权威端重新读取实体、归属、阶段和规则；观众与旧身份的伪造请求必须拒绝。

### B4. 事件、随机、保存与恢复

- 行动事件名称、公开／私人字段、顺序与修订号：［填写］
- 请求 ID 去重、预期修订、并发行动及未知回执核对：［填写；结果不明时先读状态，不自动再做一次］
- 每次随机结果怎样产生、何时持久保存、怎样绑定对局／行动／阶段：［填写］
- 随机结果后的选择怎样保存？刷新、重试或换设备是否仍面对同一个结果？［填写］
- 正式存档、草稿、共享预览的生命周期和隔离键：［填写］
- 断线、重启、暂停、超时竞争、过期选择及损坏存档怎样恢复：［填写］
- 保存成功但响应丢失时如何避免重复发牌、掷骰、扣款、成交或换手：［填写］

随机数不是客户端动画的副作用；重开页面或重复同一请求不能重新抽一个更有利的结果。临时预览有明确失效条件，不得被误恢复成正式行动。

### B5. 页面与手机交互

按阶段写用户能看到的内容、主要行动、不可用提示和结束后的出口。保留准确回合／阶段／待回应状态，并分别说明：

先按角色／阶段列必见信息与可用动作，而非只列组件。准备室至少明确房间号、邀请、成员、准备／开始、退出的位置及短屏替代出口；Step 0用实际共通模块验证这些要素与布局后，再扩大完整实现。维护者按[设计教训的执行入口](lessons.md#执行入口先画面再扩实现按证据交付)补适用反例，朋友无需承担基础界面验收。

- 桌面或棋盘的逻辑坐标、横竖屏投影、密集内容与放大阅读：［填写］
- 旋转后的阅读重排与共享位置是否分开？明确整理或拖动的布局在哪个确认点保存？［填写；只改视角不应偷偷改牌局］
- 点击、触摸、拖动、多选、拆并、自由摆放是否需要；不需要的明确排除：［填写］
- 如有拖影，它可显示什么、如何去除交互和秘密、哪些情形清理：［填写］
- 私人排序、自由位置、推荐与可出高亮是否需要；提示搜索范围和确认权：［填写］
- 草稿／未确认预览／已保存行动怎样区分，取消和撤销怎样反馈：［填写］
- 新到材料、最近公开变化、隐藏揭示和恢复跨过事件怎样提示，哪些不能猜：［填写］
- 错误、保存中、失去行动权、待多方回应时控件如何变化：［填写］
- 聊天与声音、手机安全区、软键盘、后台及安装体验：［引用平台，并写本游戏特殊要求］
- 共通能力的适用模式、实际模块／控件／样式、布局依赖、状态归属及不适用原因：［按平台的[接入记录](platform.md#共通能力接入记录)填写；不只写“复用”］
- 图案、数字、颜色、字体与鬼牌等特殊实体怎样区分？素材来源、统一尺寸、失败替代以及正常／拖影／预览／放大展示怎样验证？［填写］
- 每类游戏事件对应什么文字、高亮和声音？哪些只有本人听到，哪些所有成员可听，重连历史怎样去重？［填写差异，沿用平台已有能力］

视觉布局不得改变规则顺序或正式位置；拖影、动画、推荐和声音不产生业务行动。小屏测试要测真实文字与按钮可见性，不能只看外框在屏幕内。

### B6. 可选模块：只填本游戏采用的部分

**多阶段回合与持久选择**

列出阶段图或顺序、每阶段行动者、必做／可选动作、超时默认选择和中途恢复点。随机结果、费用或已揭示内容一旦确认，后续取消不能把它们退回未发生。未完成选择是否阻止换手须明确。

**交易、竞价与多方确认**

说明发起者、全部必要同意者、可交易对象、所有权与价格校验、报价版本、截止时间、拒绝／撤回，以及当任一对象已被其他行动改变时如何失效。所有同意针对同一版条款；最终成交和转移原子完成，不能先扣甲再等乙，不能由发起者代替别人确认。

**资产、货币、债务与破产**

说明每种资产的唯一所有权、整数货币单位、银行／系统资金来源、合法收费与发放；列出每次交易前后守恒或已记录的生成／销毁。欠款阶段、变卖／抵押顺序、多个债权人优先级、无法偿付与资产接收者都必须由玩家规则确定。模板不预设大富翁的起始金额、债务优先级或破产条款。

**玩家退场与继续排名**

区分离开房间、暂离、认输、游戏内淘汰／破产。说明退场者是否保留房间席位、还能看什么、哪些回应权立即撤销；其他人继续游戏的轮序、结束条件、名次与并列要有完整规则。不能因为一人出局就默认整间房中止。

**系统角色与自动玩家**

分别定义银行、牌池、主持者或自动玩家可执行的规则动作与数据权限。系统不是一个凭空拥有全部玩家权利的真实账号；自动玩家只能获得规则允许的投影，后台恢复不能重复执行或抢用户的新行动。

**隐藏信息与同时行动**

列出私牌、秘密目标、暗标、密封报价或同时选择的读者范围、揭示时机和先后决议。别人的未提交选择不能从提示、请求结果或时间顺序泄露；断线／超时的缺省处理必须由规则确定。若要公开验证随机或封存结果，另外写清验证数据及公开时机。

### B7. 失败与验收

给每个确认规则至少一项可重复验收。每项写“初始状态／身份→行动→预期正式状态、投影和页面→如何证明”，不要只写“功能正常”。

- 正常完整一局，开局参数上下界，全部阶段与结局／并列：［填写］
- 每类合法／非法行动、未定色／隐藏／无合法行动等边界：［填写］
- 伪造实体、越权、旧账号、观众、旧回合及秘密置换后提示不变：［填写］
- 守恒、完整存档恢复、旧版本继续、新局隔离与损坏拒绝：［填写］
- 同请求重试、并发冲突、响应丢失、随机结果后重连、超时竞争：［填写］
- 草稿取消与正式保存、多人回应失效、退场后继续游戏：［填写适用项］
- 实际 HTTP／事件流确认后刷新，电脑和手机竖横屏、原生触摸与软键盘：［填写］
- 自动化规则／状态／权限测试入口与人工验收步骤：［填写公开相对路径］
- 共通接入的实际模块、替身依赖和对应证据：［分别记录调用测试、真实 HTTP／SSE、本机页面组合与真机结果；未运行层保留待验收］

记录实际运行的设备和方法。模拟视口、合成键盘或合成指针只证明相应条件，不能写成真机触摸、真实输入法或真实声音已经通过。

### B8. 可以开始开发与可以交付的条件

进入完整实现前，Step 0样板与上屏验证已通过；影响合法动作、秘密、守恒、结算和超时的关键未知已有人工结论，其余待定项有明确范围，不被 AI 默认填完。开发者将玩家规则与逐项内容定义映射到状态和验收，朋友能确认是他们要玩的版本；本轮全部可入局定义及资源在完整接入前齐备。

交付前，规则、页面、权限、保存和失败用例都有结果；明确区分已实现、已测试与未验证环境。设计使用仓库内相对链接和可公开来源，不放账号、凭据、生产端点、私人截图证据或本机绝对路径。更新[设计入口](./README.md)与适用的公开说明，由维护者决定合并和发布。

### B9. 开发前一起过的经验检查

这一节由维护者和玩法设计者一起核对，来自[拉密与军棋的迭代经验](lessons.md)。不用先写代码；每项写结论与一个例子，不能只打“已考虑”。不适用时注明原因。

1. **完整约局和出口**：等待、进行、暂停、结束、练习各自怎么离开？返回大厅、退出房间、认输、退出登录有什么不同？房主和最后玩家离开怎样处理？［结论／例子］
2. **所有改变胜负的例外**：首次条件、特殊牌或棋、材料耗尽、无合法动作、并列、超时怎样判断？地方规则由谁确认？例如镜像 13 计分、工兵全灭之后怎么办，都应在规则实现前定好。［结论／例子］
3. **每种操作的完整结果**：点、拖、整组移动、插入、抽出、拼接、拆分、撤销需要哪些？以具体实体和落点演示，说明自动辅助的边界；没有这些操作的游戏明确写无。［结论／例子］
4. **四种状态的归属**：正式状态、私人草稿、显示布局、公共预览分别保存在哪里、何时确认、谁可见、何时清理？整理后结束回合、摸牌不提交草稿、另一设备恢复分别得到什么？［结论／例子］
5. **一屏与方向变化**：哪些区域必须同时可见，材料最多时怎样阅读，小屏与平板怎样重新布局？旋转不能改变实体、正式分组或私人操作意图；键盘出现时输入和发送怎样保持可见？［结论／例子］
6. **反馈与提示来源**：当前行动者、合法目标、未确认、已确认、最近别人动作、新消息、本人消息和结局分别怎样提示？声音只是补充，静音时也能辨认；公开声音与本人声音分开，历史不补播。［结论／例子］
7. **公私和角色边界**：玩家、队友、观众、房主各能看和做什么？秘密实体、合法目标和错误提示会不会泄密？两个同名账号不能互认座位。［结论／例子］
8. **失败与中途恢复**：重复点击、保存成功但没收到回复、断流、后台、失效登录、临时不可用和换账号各保留什么？随机结果或多步选择不能靠刷新重做，旧局不能被新规则重解释。［结论／例子］
9. **资源和证明方法**：Step 0样板和操作小样是否通过，本轮全部可入局类型是否都有定义与资源，特殊实体能否辨认，正常画面、拖影、预览、放大是否都能加载？每个关键例子用哪种测试证明，哪些必须真机或多人联合？［结论／例子］

**适合前期定好的内容**：规则、角色权限、状态归属、确认与撤销、保存时点、超时、退出后果、布局策略和事件反馈。先用局面例子或小原型验证有分歧的交互，再做完整实现。

**需要实测后完善的内容**：真实手机软键盘与手势、音效听感、密集画面的触摸准确度、性能和系统后台恢复。前期先定验收方法与可接受行为，保留专项验证；不能靠一份设计保证所有设备一次完美，也不能把这些问题等到朋友随意游玩才检查。
