# 共通房间布局规范

适用于拉密、军棋、飞行棋、你画我猜、两副牌414、幽街商人及后续游戏的正式房间与独立练习；覆盖准备、对局、观战、暂停、结果、设置和聊天。本文是设计与验收合同，不表示现有页面或设备已经全部通过。权限、保存和离席后果仍按[共通平台](platform.md)，游戏内容按各自设计。

## 1. 固定三个操作层级

这三层同时遵守[操作与动态体验规范](gameplay-experience.md)：游戏物件优先承载操作，临时决策就地展开；领域待选状态不决定采用表单或弹窗。布局要提供对象从来源到结果的连续空间，不能仅把所有按钮放进正确区域。

- **房间级**：身份／房间与连接状态、聊天、设置、退出。跨游戏与阶段使用相同位置和顺序；退出保持独立可见，不能藏进设置、规则或更多菜单，也不能与结束回合共用一个按钮。
- **游戏区局部**：牌架整理、放大、画笔、橡皮、棋盘视图等，放在它所影响的区域旁。只有当前角色能用的工具才提供操作；观众有明确只读状态，不留下可提交的假入口。
- **本轮主要动作**：准备／开始、出牌／摸牌、掷骰、提交选择、回应、再来一局，贴近当前任务和反馈。主次由当前阶段决定，不能为了工具栏整齐把所有动作移到房间级。

每个阶段先列“必见信息、主要动作、局部工具、房间出口”四项，再决定排版。准备室的房号、邀请、成员、准备／开始、退出都要有可见入口；房号不能只挂在小屏会隐藏的连接文案里。结果页保留结果、再来／返回和退出；观战页保留角色、局面和房间工具。本机练习使用“练习／保存状态＋设置→退出”，不虚构聊天、房号或邀请。

必见要素从规则的决策需求生成，不能只照已有DOM列清单。涉及对手货物、道具、容量或持续效果的动作，须在主画面同时保留其公开信息与本人资源，不能用“库存总量”代替所需分类，或用短屏隐藏对手栏解决高度不足。详情负责完整牌文，不替代判断目标所需的常显信息；观战显示双方公开区，不将其中一方当作“自己”，也不增加私牌权限。

## 2. 房间工具栏的固定合同

从左至右为“状态区｜右侧动作组”，动作组内部固定“聊天→设置→退出”；无聊天的练习移除该项，其他顺序不变。状态区可伸缩，动作组保持紧凑。横竖屏、阶段切换、长昵称／状态、消息角标出现时都不能交换逻辑顺序。

- 同组相邻控件间距为 **6–8 CSS px**，组内垂直居中；退出前允许 **10px** 间距（8px组内间距＋2px出口分隔），其他动作不沿用该例外。可以在状态区与整个动作组之间分配剩余宽度；禁止把每个动作作为同级子项用 `space-between` 撑满整条工具栏。
- 房间工具的点击区至少 **44×44 CSS px**；图标按钮固定44×44，文字按钮固定44px高度，宽度按文案预留且不被 flex 压缩。普通控件沿用共通10px圆角，图标／文字在点击区内居中；不能只把透明外框做大，却保留偏心的图标或不相符的命中区域。
- 44px是**本项目操作目标标准**，不是对WCAG最低尺寸的转述。字号、角标与主题变化不能压小点击区；长状态允许合理换行或收纳，关键房号／阶段／未确认错误另有可读出口，不能用裁剪吞掉必要信息。
- 窄屏需要换行时，优先让状态区独占一行，动作组整体右对齐；动作组不拆散、不均分。视觉顺序、DOM顺序和键盘焦点顺序一致，不能用CSS重排制造相反的操作顺序。
- 设置与聊天的关闭入口也保持44×44、居中、可辨名称。长列表或软键盘出现时，关闭、输入、发送和反馈仍可达；弹层只保留当前一层，收起后回到合理焦点。
- 设置里的普通按钮和“标签＋选择＋提交”等复合控件混排时，不能被相邻项拉伸成无意义的大按钮；保持内容起始对齐，多行文字按自身内容增高。

共通几何由[控件样式](../../app/platform/control-geometry.css)负责，设置由[房间设置](../../app/platform/room-settings.mjs)、聊天由[房间聊天](../../app/room-chat.mjs)装配；主题只改变颜色与材质。新游戏不得复制一套接近但顺序、尺寸或清理行为不同的工具栏。组件文件存在或被导入，不能证明真实页面已满足合同。

## 3. 转屏要保留阅读与操作

转屏、窗口拉伸和浏览器缩放只改变显示投影，不改变实体ID、正式顺序、分组、已选择对象、草稿意图、回合或共享坐标。工具逻辑顺序不变；重排前后的关键信息和主要动作都可见可用。检查首次竖屏进入和横→竖→横，不能只测转过一次后的画面。

手牌、棋盘和画布不能为了“框在屏幕内”无限整体缩小。设计须填写本游戏的最小可读实体宽高／文字尺寸和测量场景；密集时先重排显示或提供明确可操作的放大／分页阅读出口，不得缩成无法辨认或选中的小点。实体的阅读尺寸与工具按钮的44px标准分别验证。

拉密的自由手牌须以跨整个旧宽度拖散的局面做往返转屏：不能按旧坐标包围盒把所有牌一同缩小；本机阅读重排保留实体、顺序、选择和私人操作意图。单纯旋转不保存公共位置、不提交草稿。检查普通手牌、较大手牌、自由摆放和恢复旧布局，不能只用自动整理的整齐牌架证明自由布局。

主屏核心区域一屏可操作；聊天历史、设置正文可内部滚动。不得以 `overflow:hidden` 裁掉必要内容、无限缩小整个页面、把主要动作移出屏幕或禁用转屏来宣称适配完成。

### 受控游戏舞台与支持范围

先按内容和操作关系设计少量稳定构图，再适配实际视口；窗口每变化一个比例不新增一套局部补丁。输入分类覆盖4:3、3:2、16:9、16:10、21:9、32:9，以及手机长屏和平板横竖屏；同类可复用构图。超宽空间可以承接桌布、辅助公开区或留白，不把卡牌、画布或单个按钮拉长。

- **量实际内容区**：布局依据浏览器可用内容区的CSS像素、方向、键盘和安全区；记录宽高，不用显示器标称物理分辨率代替。物理像素、DPR、系统缩放与浏览器缩放分别登记；相同1920×1080屏幕不保证相同可用高度。
- **桌面FIT有下限**：本游戏明确设计宽高、构图选择、`scale=min(可用宽/设计宽,可用高/设计高)`、放大上限和最低支持尺寸。等比缩放只作用于游戏舞台；房间工具、聊天、设置及输入辅助有独立可读空间。按缩放后真实点击区、效果正文和牌面尺寸核下限，不能只量缩放前44px。下限不足先切紧凑构图，再明确提示扩大窗口或全屏；不宣称极小窗口仍能完整玩。
- **手机独立构图**：不把完整桌面缩成手机微图；沿各游戏已确认方向与触摸方式，保留44px操作目标、关键牌效和可辨实体。软键盘改变可用高度但不误判为需要旋转，不挤掉输入、发送或当前任务。安全区计入可用空间，不遮物件和出口。
- **展开状态有预算**：同时容纳对手公开区、当前来源牌、效果／费用／后果、确认动作及本人手牌。空桌和首摸截图不能证明完整选牌、回应、拍卖或多材料步骤可用；长文案先去重复或分步，不能靠裁剪、隐藏对手或缩字补高度。
- **坐标只有一个解释**：命中与动画统一使用视口坐标或明确转换到舞台逻辑坐标，不能混用。缩放舞台与未缩放overlay分开；`clientX/Y`、`getBoundingClientRect()`、fixed拖影、画布采样及动画终点逐项核同。连续resize取消临时拖影、重算布局，保留正式状态和本机任务草稿；不发游戏行动，不补播历史声音，不因DOM重建丢焦点／选区。

每个游戏在技术计划记录实际构图、可读／点击下限、支持尺寸、极小窗口行为与消费者。当前整改见[视口适配计划](../plans/viewport-adaptation-v1.md)，该计划的实施和验收结论不由本规范代替。

## 4. 每批检查入口与完成条件

新游戏计划及每批共通布局修改先列**实际消费者清单**：页面／控制器、正式或练习、玩家或观众、相关阶段、共同组件与样式、差异和验证入口。当前基线是六款游戏的十二条正式／练习页面路径；准备／结果等动态状态也属于消费者，不能只枚举HTML文件。当前源码入口见[游戏目录](../../app/game-registry.mjs)及[架构](../architecture.md)。

1. **基本要素与操作**：实际进入受影响页面，展开准备室、主屏、设置／聊天和结果等适用状态。逐项确认房号／邀请、角色／阶段、主要动作、退出及反馈仍有出口，实际点击一次适用动作；练习确认没有假聊天。
2. **真实几何**：读取最终DOM的 `getBoundingClientRect()`、计算样式和可见状态，记录目标宽高、间距、对齐、圆角、文字／图标、焦点及遮挡；测点击目标本身，不能只测其父容器。固定按钮不缩小、间距为6–8px（退出前允许10px）、动作组顺序正确；状态长文案与角标出现后再核一次。
3. **截图与阅读**：留下展开截图并实际检查，至少覆盖桌面、窄竖屏、短横屏与一次转屏往返；本批再选一个最有风险的长文案／密集局面／软键盘组合。视口合同变化还覆盖常见分辨率、宽而矮的桌面，以及展开任务中的连续拉伸／跨构图边界；风险组合足够，不要求尺寸×主题×状态全排列。逐区核标题、关键文字与实体的纵向完整包含；允许横滑的牌带还要实际到达首末牌。不能只查当前任务或整个页面没有溢出，局部`overflow:hidden`可能掩盖手牌被挤到下一行。工具栏无溢出但手牌不可读、来源牌或确认按钮被截断、缩放后点击区不足44px，仍是失败。
4. **可执行证明**：记录检查脚本的实际路径、完整命令、前置启动方式、合成数据范围及证据输出位置；脚本必须实际执行，静态语法通过或一段未执行的检查代码不能写成布局通过。手动浏览器检查记录可重做的具体步骤和结果，不能填“注意UI／已检查”。
5. **结论范围**：每项用“场景→实际模块／页面→预期→方法与环境→几何／截图／操作证据→通过、失败或待验”记录。本机规则、真实本机浏览器、模拟视口、真机触摸／输入法、真人及线上分别下结论；本地修复与文档落地不表示已部署或真机通过。

共通修改逐项核全部受影响消费者的基本画面和动作，风险尺寸做代表组合；未改变且有有效证据的范围不无故重跑。失败先修复并重验影响面，缺环境则保留具体待验项，不能用测试总数填补。

对手信息相关修改至少以双方各自视角、观战和实际练习检查小屏：空／满装备、同名道具各自可用／横置、分类货物及回合效果变化均可辨。沿“权威公开投影→展示投影→共用页面→实际控制器”核字段与点击结果；对手道具只读牌文，不能出现使用／安装动作，私牌和私看候选仍仅对有权限者可见。

**六套主题均须适配**：森林布、月夜蓝、石墨、樱花米白、原木织纹、海盐使用相同的尺寸、间距、顺序和命中区；逐套核对实际前景／背景颜色与可读对比，包含状态、提示、按钮和游戏内容。选中、禁用和键盘焦点保持可辨且不只靠颜色；展开设置／聊天核正文、关闭入口、遮罩与前后层次，不能因浅色背景、材质或主题覆盖让文字、焦点、下拉箭头消失。每套留实际样式／几何结果，深浅主题及发现差异的主题留代表截图和操作结果；主题色板通过不能代替真实页面，未运行的主题或设备明确待验。

仓库内的[布局检查脚本](../../scripts/room-layout-audit.mjs)使用隔离内存房间、合成身份和真实页面，输出JSON几何／操作结果及PNG；截图仍须人工目视，脚本不判断“好看”。从仓库根目录使用现有Playwright与Chrome运行，不自动安装浏览器或新增运行依赖：

```sh
GAME_ROOM_PLAYWRIGHT_MODULE='<现有 Playwright 的 index.mjs 路径>' \
node scripts/room-layout-audit.mjs --output '<本地证据目录>'
```

环境已有可导入的Playwright时可省略 `GAME_ROOM_PLAYWRIGHT_MODULE`；`GAME_ROOM_BROWSER_CHANNEL` 可选择已安装浏览器。具体覆盖与失败以当次输出为准；此命令是本机检查入口，不代表该批已执行、真机或线上通过。

## 5. 必须保留的反例

- 状态、聊天、设置、退出分散到四角或被 `space-between` 均分；转屏后顺序颠倒。
- 外框44px但图标偏心、命中框缩小；同一设置里的链接仍是左上角原生文字。
- 短屏把连接栏／footer隐藏，房号、邀请或唯一成员／结果入口随之消失。
- 自动整理的手牌可读，自由拖散后转屏却整体缩成小点；只测边界不测实体和字的大小。
- 只测标准比例或空桌；宽而矮窗口展开完整选牌时，中央内容被固定手牌栏和对手区挤掉，外框仍在屏内。
- 只查看未登录首屏、只跑规则／结构测试、只证明“已导入共通组件”，未展开设置和聊天、未操作准备／结果出口。

## 参考采用范围

[W3C一致导航说明](https://www.w3.org/WAI/WCAG22/Understanding/consistent-navigation)用于保持重复导航的相对顺序；[Apple工具栏指南](https://developer.apple.com/design/human-interface-guidelines/toolbars)用于按用途组织、分组并保持工具可识别。本文将这些原则落实为项目自己的三层职责、右侧动作顺序和几何标准；不把工具栏约定或44px数值冒称为来源对所有场景的统一要求。
