# 两副牌 414 技术实施计划

2026-10-08 编写，2026-10-09 评审并开始实施。本计划是两副牌 414 的唯一实施进度入口：当前已接通资源、规则、持久房间、永久积分和真实多人页面；尚未正式开放或部署。实际证据与未完成项见第11节。实现依据为[两副牌规则](../design/games/poker414-2.md)的 `poker414-2-v2`，计分版本 `poker414-2-score-v1`；文件名 v1 表示首版实施计划，与规则版本区分。

计划编写时的代码调查基线：main `c6a266e`。读取[实施计划模板](game-implementation-plan-template.md)、[架构](../architecture.md)、[平台设计](../design/platform.md)、[经验检查](../design/lessons.md)及下列真实模块。下文的目标合同不等于已接通能力；尤其拟新增平台与存储接口仍待实施，不能把计划当作已通过的测试证据。

## 1. 首版范围与完成定义

- 仅 `gameType: poker414-2`，3～8 位玩家、最多 8 位观众，108 个实体；一副牌只作为已确认基础规则的引用，不同时制作一副牌入口。
- 包含完整发牌、首张红桃 3 先手、逆时针轮序、普通牌型／三至八张炸弹／三档火箭、最多八张交替勾叉、唯一合法组合辅助选中、永久娱乐积分、观战、邀请、聊天、设置、恢复、再开和离开。
- 普通回合无时限；勾叉窗口 5 秒；没有暂停、托管、机器人或新的收费服务。连续失联 120 秒零分取消；主动离开按已确认规则向其余参赛者每人赔 5 分。
- 观众可看全部已发手牌，玩家只看本人；此例外必须由服务端投影授权。当前房主和中心管理员不额外获得看牌或出牌权限。
- 首版不做本机练习或 AI 对手；公开目录使用现有合法值 `practicePage: null`。大厅不得展示虚假的可练习入口，规则页提供静态例子。教学模式如后续需要，另补设计。
- 完成定义是“从大厅邀请到结算／离开的一整局可用”：准备室房号和邀请可见、所有角色有出口、密集手牌可选、抢响应不重复扣牌、结算永久保存。规则引擎通过不等于完成。

## 2. 已有能力与必须补的缺口

- [房间核心](../../app/rooms.mjs)和[注册表](../../app/game-registry.mjs)按适配器决定人数；你画我猜已有八人，因此不需要修改其他游戏人数。观众上限仍为 8，实际连接容量另验。
- [适配器合同](../../server/games/adapter-contract.mjs)已有动作、独立公私视图、存档和历史校验；绘画已有 `concurrentActionTypes` 和可选阶段时钟。但 `syncClock` 当前无旧 clock 就直接返回，不能保证无普通时钟的 414 后来成功创建响应窗口。
- 共通 leave 当前中止且零分，`aborted` 不产生计分结果；暂停默认可用。这些都不能直接套给 414。
- [持久房间](../../server/durable-rooms.mjs)已有多连接 presence、CAS、本人意图回执、定时推进和归档 outbox；没有“任一参赛者连续失联 120 秒后零分取消并回准备”的业务策略，进程重启也不会自动按 414 规则取消旧局。
- [战绩服务](../../server/match-history.mjs)保留 180 天，且逐索引归档；不是永久积分账本，不能对最近战绩求和冒充累计分。
- [存储](../../server/storage.mjs)已有 `compareAndSwapMany({changes, guards, validUntil})`，SQLite 使用真实事务；最多 64 个唯一 key、32 MiB 密文。本项目可在现有存储内完成结算，不需要新数据库。
- [页面排序与时钟文案](../../app/platform/room-presentation.mjs)默认按游戏玩家数组的下一项和 clock 首位展示；默认到期文案是“正在换人”。414 要显式提供实际逆时针行动序列，并将响应关闭与普通换手区分。
- [公开目录](../../app/games/catalog.mjs)、[静态白名单](../../server/public-assets.mjs)、大厅路由和原／同域入口都需要登记新页面，不能只新增一个 HTML。实际共通装配见第 8 节。

## 3. 模块与状态所有者

目标游戏目录 `app/games/poker414-2/`，各项实际进度见第11节：

- `cards.mjs`：54 种牌面类型及 108 个实体的纯定义；牌面不决定权限。
- `patterns.mjs`：牌型识别、比较与本人合法组合枚举。按点数计数及连续区间枚举，不穷举 36 张手牌的全部子集；火箭等价类包含三档等级。等价实体按稳定 `copyId` 选择，玩家改选不被覆盖。
- `rules.mjs`：完整权威状态机；洗牌随机源由服务端注入，客户端不能提交骰子式随机结果或完整牌局。
- `art.mjs`、`presentation.mjs`、`page-ui.mjs`、`styles.css`：原创牌面、只读显示模型、页面与布局。呈现层仅获得本角色投影，不能导入完整引擎或其他人的手牌。
- `game-page.mjs`：装配既有会话、RoomClient、动作意图、退出和聊天；不得复制账号或 SSE 实现。

服务端拟新增 `server/games/poker414-2/adapter.mjs`，以及跨游戏可复用的 `server/game-scores.mjs`、窄只读入口 `server/game-scores-http.mjs`。积分服务只接受经适配器验证的终局摘要，不能按客户端分数记账；`accountGroup: 4a4` 供将来一副牌共用，其他游戏不自动加入。

允许依赖为：房间装配 → 适配器 → 414 纯规则；持久提交 → 积分事务服务 → 存储；页面 → 公开呈现与平台工具。共通模块通过显式合同调用差异，不增加散落的 `if gameType === ...`。

四类状态明确分开：

1. 服务端权威：`matchId`、规则／计分／schema 版本、固定参赛者、座位与行动序列、洗牌顺序、发牌游标、首张红桃 3、各手牌、全部已出实体、当前目标／拥有者／来源、普通行动者、不出记录、响应窗口、公开行动历史和终局摘要。
2. 本机草稿：选中牌、放大面板及布局投影；按账号、房间、对局和目标隔离。目标变化重新验证选择，明确过期则清除；重连不把草稿当成已出牌。
3. 临时连接：presence、连接 ID、身份核验和声音授权；不进入业务备份，不以昵称恢复。
4. 持久累计：积分账本、余额与容量预留归积分服务，不能跟房间过期一起删除。

## 4. 平台扩展合同

以下是最小拟扩展点，阶段 1 用真实装配测试冻结签名；不一次重写整个房间平台。

### 4.1 阶段与时间

房间阶段继续为现有集合。414 的发牌使用 `room.phase=playing`、`game.stage=dealing`；此时名单已锁定，离开已适用赔偿。正常出牌为 `game.stage=playing`。这样不会把已开始发牌误当作等待室。

适配器的 `gameClock` 在每次状态变化后同步，可返回 null 或 `{kind, id, deadlineAt}`：普通出牌无窗口时 null；发牌下一批为 `deal`；勾叉为 `response`。先检查适用动作与期限，再做提交守卫；响应到期只清窗口，不替玩家“不出”，也不换普通行动者。截止规则固定为服务端提交时 `now < deadlineAt`，等于截止时间即拒绝响应。response期限只约束fork/hook；普通play/pass遇过期窗口先由服务器关闭窗口，再核对同一match、round、target和行动者，不能套用原TURN_TIMEOUT把普通出牌也限成5秒。仅清窗引起的修订变化走明确的414业务前提校验，其他普通动作冲突仍拒绝。

发牌拟采用保存一次洗牌、按逆时针逐张分配、分批推进游标：初始方案每 500ms 最多推进 18 张，共六批；不是逐张做 108 次网络提交。每批只公开已发前缀，第一张红桃 3 进入前缀时固定先手；最后一批与进入出牌阶段原子提交。动画只重现已确认顺序；延迟恢复直接赶上已确认进度，不补发 108 声音。批量大小与节奏在阶段 0 的有界实验中决定，改变节奏不改变牌序或分配。

明确 `seatOrder`、逆时针 `actionOrder`、`firstPlayerId`、`turnPlayerId` 和 `nextPlayerId` 的关系；屏幕将本人放到底部只旋转投影。共通排序接收显式行动序列，不能依赖有没有 clock 才显示正确次序。

### 4.2 共同行动与生命周期

拟增加适配器 `commonActionProblem(...)` 与 `lifecycleTransition(...)`：前者限制暂停／继续等共同行动；后者按原因返回中止、取消、结算及是否回准备的权威变更。旧四款缺省仍走现有路径，明确未声明能力的游戏不得获得赔分或全知观战。

- 主动中止、页面返回大厅、退出房间：发牌开始后至终局前，确认框显示实际人数对应的本人扣分和其他人所得。必须由独立退出控制提交明确 leave；保存赔分结果后才释放席位和导航。等待和结算后免费离开。
- 设置中的“返回大厅，保留席位”不适用于本游戏；品牌链接、返回按钮和退出叉均进入同一离开合同。浏览器后退属于可能没有收到明确 leave 的离开，不能凭 `pagehide` 直接罚分；保留席位并按真实失联规则处理。回到页面先读已确认状态，不能复活取消局。
- 退出棋牌登录仍是账号动作，不冒充已确认的赔分 leave。进行中从本页面主动点击时，先解释并执行本局退出，成功后再调用既有单项目退出；过期被迫重登和 401 不算主动中止。
- 观众退出不取消牌局、不赔分；最后房间成员离开按平台回收。房主退出和转交仍由房间平台管理，不能留下无人可重新开局的等待室。
- 任一参赛席位的所有连接都失效才进入失联判定；保存该席位最后一次服务端确认存活的 `lastSeenAt`，取消界限为 `lastSeenAt + 120000`，不能每次轮询重新起算。现presence租期10秒用于确认连接已失效，计入上述120秒，不再额外加120秒；其他设备仍在线不触发取消。先断开再恢复的状态变更必须更新服务端时间与版本，不能用客户端自报时间。
- 达到 120 秒后，以 room、match、presence 版本共同核验并原子零分取消；取消后全体准备状态清零，房间回 waiting，保留稳定成员与最近取消原因，再开使用新 matchId。重连与取消并发只允许一个已核验结果。
- 进程启动或故障恢复时，对未完成 414 局执行零分取消并归档后回准备；不续打旧局、不重洗成同一局。已经提交的正常／赔分账本必须先对账，不能被启动取消覆盖。

修改共通时间或生命周期时，旧四款回归之外，扩展现有[独立最小游戏测试](../../app/game-platform-boundary.test.mjs)：覆盖无回合 clock 后动态产生非换手期限、非当前玩家响应与不同中止结果，证明合同不靠 414 名称分支运行。

## 5. 动作、并发与公私输出

复用现有房间 action POST、状态 GET 和 events SSE。新业务字段统一白名单；每次提交包括 `requestId`、`expectedRevision`、`matchId` 及当前业务对象标识。客户端不能提交自己的 `userKey`、结算分数、牌库或新的窗口截止。

- `play`：当前普通行动者、出牌阶段；提交实体 ID 数组、`roundId/targetId`。实体唯一且属于本人，牌型合法且能压目标。原子移动牌、记录事件、清不出记录、更新目标与轮序，优先判断清空手牌。
- `pass`：当前跟牌者、目标仍相同；不允许领出时不出。不移牌、不重置窗口；全员不出形成新轮时关闭旧窗口。
- `fork/hook`：任何有资格的参赛者、有效目标／窗口，且不是当前合成拥有者；提交 `targetId/windowId`，由服务器取两张／一张实体。验证来源、交替、同点数和八张上限，再更新合成与拥有者；未终局且还能继续时开启新 5 秒。
- 准备、开始、角色、转房主、再开、leave：保留现有平台权限；进行中不能改观战来逃避离席结算，观众不能借房主身份进入出牌动作。
- 到期、发牌推进、失联取消、故障恢复：只有服务器系统路径可发起；客户端刷新可以请求最新结果，不能自行宣布超时或别人掉线。

使用 `usesActionIntents` 的本人回执与 [RoomClient](../../app/room-client.mjs)／[意图工具](../../app/platform/room-action-intent.mjs)。同请求 ID、同正文返回既有结果，同 ID 换正文拒绝；未知结果先只读对账。超出有限回执保留范围时，按固定对局／终局账本查询，不能换 ID 补出一次。

勾叉可采用现有 `concurrentActionTypes` 的业务前提模式：仍传 expectedRevision，但普通不出或无关房间资料变更导致 revision 更新时，只要 match、target、window、期限和手牌前提仍成立，可针对当前存储版本重新验证并提交。普通出牌／不出不一概绕开版本；任何冲突不得把旧选择改投新目标。

必须实际验证以下竞争：两人同时叉只成功一个；勾后旧叉请求不能自动变成新叉；第 4999ms 请求到达但提交已到截止时拒绝；不出改变修订但未关窗仍可响应；最后一手、主动离开、120 秒取消三者竞争只能形成一个终局账本。414业务提交的CAS冲突重读最多两次，仍冲突返回可恢复错误，不无限循环，不把未提交候选广播出去；不全局降低旧游戏、profile或共通leave的现有重试预算。

投影以当前身份与角色生成：玩家只收本人手牌及其他人的数量；观众可收全部已发手牌；双方都不得收到未发顺序。公开行动只引用已出的实体。错误、聊天气泡、音效、日志和规则提示不夹带私牌。角色变化、401、503、换账号及迟到 SSE 都要清除旧全知／私有 DOM，恢复时重新取合法投影。

SSE 可合并快照，所以公牌与合成链不能仅依赖一次性事件通知。游戏快照保存全部已出实体和出牌／响应来源；最多 108 次移牌行动。不出事件和系统通知另设有界序列，初值上限 1024，保留当前轮所需前提；完整公牌不能随通知裁剪丢失。以 `matchId+eventId` 去重，恢复直接渲染最新场面，不重播历史声音。

## 6. 永久积分、存档与恢复

### 6.1 结算事务

拟新增三个明确 scope：`game-score-ledger`（不可变分录）、`game-score-balances`（余额）、`game-score-meta`（版本与容量预留）。余额键使用 `4a4:<userKey>`，分录使用 `4a4:<matchId>:<settlementVersion>`；禁止以昵称、显示名或临时席位作为账户键。所有参赛者来自开局冻结的 `matchParticipants`，观众不入账。

正常、主动中止和系统取消都产生唯一终局摘要；正常／赔分更新余额，取消保存零分原因。正常罚分使用规则公式，赔分只计算责任人每位 5 分，不能叠加余牌分或错误计算胜负。

在 [durable-rooms](../../server/durable-rooms.mjs) 保存终局的真实提交点装配积分事务：一次 `compareAndSwapMany` 写房间、唯一分录、最多八个余额、该局已应用结算版本头和容量记录，至多 12 个写 key；会话／presence 等守卫也计入 64 个唯一 key 上限。分录不存在条件、余额读取版本、房间／对局版本和必要期限一起核验；成功之后才 publish，再由现有 `pendingRecords` 归档战绩。

两房间给同一账号同时结算时，以余额版本重读并原子累加；不能用每房间内存锁代替。回执丢失先查询固定分录及终局指纹，既有分录只返回结果；战绩归档失败不会漏分或再次加分。`archive()` 的字段白名单、不可变比较和历史投影要共同支持 `accountGroup/scoringVersion/settlementVersion/deltas`，不是只加展示字段。

更正保留原分录，使用唯一更正 ID 和目标结算版本，只入新旧差额、检查全桌和为零及安全整数范围。`game-score-meta` 为每局保存已应用结算版本头；更正事务必须核对并推进该版本，同一旧版本的两个不同更正ID不能依次重复加差额。首版不开放玩家任意改分按钮；更正经本项目维护权限、明确操作范围与预览执行，不赋予 Agora 管理员游戏改分权。

### 6.2 存储边界与可恢复性

414 拟用 room snapshot schema11，旧游戏仍写各自格式。由 [snapshot兼容层](../../server/room-snapshot-compat.mjs)、适配器完整校验和[发布兼容声明](../../scripts/release-compatibility.mjs)一起登记；新读1～11，不能让旧1～10包误读11。

约束先取：414 单房间明文快照不超过 512 KiB、单终局分录明文不超过 16 KiB、积分总编码预算 256 MiB。这是本机实验初值，阶段 1 根据实际编码大小核定，开局前冻结。积分容量按存储最终编码payload字节计算，包含AES-GCM／base64膨胀；新增分录、首次余额、meta和更正均计入，更新按新旧字节差值记账，同一quota版本守卫并发变动。此预算不等于SQLite文件、WAL或备份磁盘总量，另观察实际磁盘余量。牌实体固定108、公牌历史有界，不允许通过无限消息或每次复制全历史扩大快照。

开局锁定名单／matchId的同一事务预留足够的最坏终局及相关余额容量：尚无余额的成员计入新行全额，已有余额计入最大增长差额；并发局可保守多预留、终局按实际释放。达到预算拒绝新局并提示维护者，不得等玩家出完牌才拒绝结算。终局事务将预留转为实际已用；回收前核对固定matchId、终局分录与房间版本，不能仅见房间不存在就释放未知结果的预留。更正另行预检容量。

现存储只接受有限的未来 `expiresAt`；永久账本／余额／meta约定使用 `Number.MAX_SAFE_INTEGER`，禁止传null或Infinity，业务不按TTL回收这些记录。备份校验保留同一值，不能借房间八小时或战绩180天TTL。

[备份](../../server/backup.mjs)从现有13 scope拟扩到16，加入逐行校验和跨记录对账：余额等于不可变分录累计、预留引用有效、终局与账本一致。继续接受旧6／7／9／13 scope文件作为历史恢复格式；其缺少新积分必须明确标识，不能拿旧备份覆盖已有永久分数或宣称完整恢复。

恢复使用原稳定密钥、独立新路径和新进程，校验全部108实体、冻结参赛者、唯一结算与积分；不恢复会话、token或presence。恢复到未完成局按故障取消，已完成局及所有已入账分保持。损坏、未知规则或不一致账本拒绝继续并保留诊断，不清库修复。

首个schema11／积分写入之前先准备能读取新格式且关闭新开414入口的兼容回退包。停止新建不能直接停掉正在玩的房间；优先允许已开局正常收口，故障时明确取消并保留账本。原旧包不具备回退资格。

声音采用现有 [game-audio](../../app/game-audio.mjs) 和 [音量控件](../../app/platform/room-audio-controls.mjs)，事件合同如下：

- 选牌／取消：本人低优先 select；提交中只有本机视觉反馈，不先播已成功出牌。
- 发牌开始：全房 start 一次；逐张不播108次，批次只用轻量可合并反馈；发完后仅先手本人 turn，其余成员看到文字。
- 出牌确认：全房 placement；勾、叉、普通炸弹和火箭增加可区分的短合成提示，按同一事件只播放一个动作音，避免音效叠加淹没通知。
- 不出：全房简短低优先提示；轮到本人 turn 为高优先。勾叉机会用常驻文字／边框和可合并提示，不能每一秒鸣响。
- 发言：沿共通 chat；自己确认气泡可见，但不重复播放收到自己的消息音。结束为各玩家 win/loss，观众及中止用中性提示；终局高于普通动作。
- 请求被拒：仅请求者 invalid；POST与SSE同事件去重，重连不补播历史；静音、未启声、系统静音和后台均保留文字。设置提供每类试听和真实声音状态。
